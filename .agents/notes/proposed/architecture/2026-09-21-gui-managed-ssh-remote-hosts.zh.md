# Agent Note: GUI 管理的 SSH 远程主机与按会话划分的执行世界

Status: proposed

[English](2026-09-21-gui-managed-ssh-remote-hosts.md) | 中文

## 问题

[POSIX SSH 运行时](../../implemented/architecture/2026-09-11-posix-ssh-runtime.zh.md)已经交付了一套可用的远程执行世界：[`dsh-ssh`](../../../../packages/ssh/ssh/README.zh.md) 持有一条 OpenSSH 连接和经过摘要校验的辅助程序，[`fs-ssh`](../../../../packages/ssh/fs-ssh/README.zh.md)、[`subprocess-ssh`](../../../../packages/ssh/subprocess-ssh/README.zh.md) 与 [`sandbox-ssh`](../../../../packages/ssh/sandbox-ssh/README.zh.md) 基于该辅助程序实现既有的文件系统、进程与沙箱服务。但没有任何 profile 或 bundle 组装它们，没有 CLI 开关选择它们，Web 客户端里 SSH 零命中。

产品想要的能力与该运行时的假设并不相同。用户想在一个浏览器 GUI 里添加若干台服务器，自己填写 host、port、user 与密钥，让 Harness 把辅助程序装到远端机器上，然后创建在指定服务器上开发的会话。而运行时只接受部署方持有的唯一 OpenSSH 别名——其 user、key 与 known-host 条目必须已存在于 `~/.ssh/config`——并且连接服务明确声明没有任何模型参数能选择这些值。

有三个结构性缺口挡住了这一能力：

- 执行服务是进程级单例。`ctx.fs`、`ctx.subprocess`、`ctx.sandbox` 与 `ctx.ssh` 每进程只 provide 一次，因此第二台主机只能以第二个进程存在，而辅助程序坐标（`host`、`node`、`helper`、`helperHash`、`workspace`）在插件加载时就已固定。
- 会话与工作区没有主机维度。[`SessionHeader`](../../../../packages/core/session/src/types.ts) 只携带 `cwd`，[`workspaceRecord`](../../../../packages/workspace/workspace/src/spec.ts) 只携带 path、title 与 session id，而工作区路径的 canon 直接调用主机 `realpath`，因此远端路径根本无法成为工作区。
- 凭证与安装分发并不存在。credentials 服务只建模 `api-key` 与 `grant` 两种记录，SSH 的 host 字段只接受别名形态的字符串，连接硬编码 `BatchMode=yes` 并对部署方自己的 `known_hosts` 做严格主机密钥校验，辅助程序只有散文式安装说明，没有工具、没有摘要命令、也没有上传通道。

此外 Web 消费方以多种方式假定了主机文件系统，一旦执行服务变成远端就会直接失效，包括用主机 `mkdir` 建新会话的 cwd、命令根取自 `process.cwd()`、主机侧目录选择器、仅主机可用的 spill 后端，以及把本机 ripgrep 二进制当作远端 `argv[0]` 解析的 glob/grep。

## 方案

在已交付的 SSH 运行时之上构建 GUI 管理的远程主机能力：一个主机注册表，为每台注册主机持有一个执行 realm；凭证在 GUI 中录入并编译成 DSH 控制的 SSH 配置；辅助程序自动安装；工作区与会话增加主机维度。

### 已定范围

| 决策 | 取值 |
| --- | --- |
| 主机拓扑 | 单个 Harness 进程内多台主机，每台主机一个执行 realm |
| 凭证 | 在 GUI 中录入：host、port、user、私钥或口令 |
| 凭证生命周期 | 只需录入一次并存储；后续连接直接复用，不再提示 |
| 辅助程序安装 | 由 Harness 自动安装，使用前校验摘要 |
| 可用性 | 默认开启，不设功能开关 |
| 会话绑定 | 工作区与会话记录携带主机身份 |
| 模型面 | 不引入 SSH 专用工具；既有能力服务仍是唯一模型可见面 |

### 主机注册表与按会话划分的 realm

`ctx.remoteHosts` 成为远程执行世界的 Service Definition。它持有主机记录、为每台主机创建与回收一个 Cordis isolate realm，并解析某个会话或工作区所寻址的执行服务。每个 realm 以该主机的坐标挂载 [`dsh-ssh`](../../../../packages/ssh/ssh/README.zh.md) 与三个配套提供方，于是 `ctx.fs`、`ctx.subprocess` 与 `ctx.sandbox` 按 realm 而非按进程解析。隔离是必需项而不是可选项：同一个服务 key 第二次 provide 会抛错，而隔离后的 realm 持有不同的 store key。

寻址按消费方分流。Agent 作用域内的消费方本就运行在 per-agent ctx 下，直接到达自己的 realm。运行在任何 Agent 之外的 Host RPC 消费方，则通过注册表按会话或工作区身份解析实例，沿用 `serviceFor(agent, name)` 这一只读寻址先例。本机保留为内置 realm，因此未注册任何主机的组合行为与今天完全一致。该能力本身默认开启：只要组装了注册表，GUI 就暴露远程主机管理，无需功能开关。

### 按主机寻址

[主机注册表](../../../../packages/ssh/host-registry/README.zh.md)是主机身份变成执行世界的唯一位置，所有消费方都通过一次调用解析：`ctx.remoteHosts.get(id).world.fs`。[工作区文件读取](../../../../packages/api/workspace-files/README.zh.md)、[应用内目录浏览器](../../../../packages/host/directory-picker-browse/README.zh.md)与[工作区控制器的分支读取](../../../../packages/api/workspace-controller/README.zh.md)都复用这次调用，因此远程工作区在其所属世界中读取，而没有打开世界的主机会以指名该主机的诊断拒绝，而不是回退到 Harness 主机自己的文件系统。

读取自己未注入的服务时使用 `ctx.get`，绝不使用属性代理：属性代理对拓扑敏感，只解析读取方 fiber 声明的内容。属于这一类并已定下的读取有两处——注册表自身由 Loader 挂载的 `apply` 中的 `ctx.remoteHosts`（该服务由这个 apply 刚刚挂载的子 fiber 提供），以及 Client 工作区 `apply` 中的 `ctx.remote.hosts`（该 apply 在没有注入这个可选命名空间的情况下构建其已选世界探测）。

### 凭证与主机密钥信任

凭证复用既有的 `grant` 记录与不透明 payload，而不新增记录类型；host-credentials 插件持有该 payload 的格式、存储与删除。插件根据已存凭证写出一份 DSH 控制的 OpenSSH 配置文件，连接侧仍然寻址一个主机别名，因此连接服务的注入面不变。凭证只在创建或编辑主机时录入一次，并跨重启持久保存；后续每次连接都复用已存材料，不再提示。

主机密钥信任采用首次使用确认：首次握手成功时在 GUI 中展示指纹并记入主机记录，之后指纹不匹配即连接失败，绝不自动接受。生成的配置固定密钥文件、端口与用户，且从不启用交互式 TTY 认证。私钥与口令不会进入 argv、进程环境或会话日志；临时身份文件以仅属主可读的权限创建，并在连接建立后删除。

### 辅助程序自动安装

安装分发是一等操作，而不是写在文档里的手工步骤。它探测远端 Node 可执行文件，在版本不受支持时给出可操作的报错，而不是去安装运行时。它把打包好的辅助程序上传到以版本与摘要命名的目录，该目录位于工作区之外、也位于可写临时根之外，符合运行时的部署约束。它在本地计算摘要，记为该主机期望的辅助程序哈希，并让远端辅助程序自算摘要、在连接就绪前完成比对。由于目录名携带摘要，重复安装是幂等的。进度与失败在 GUI 可见，且任何远端路径都不会被当作主机路径。

### 持久化与身份变更

远程主机记录存放在存储领域，与工作区同理：跨会话的事实不属于任何单个会话日志。工作区记录增加主机身份，其路径 canon 改为通过该主机的文件系统解析，而不再使用主机 `realpath`。会话创建与 session header 在 `cwd` 旁增加主机身份，这属于日志头格式变更，因此遵循 session 格式版本机制。该变更之前写入的记录按本机主机解读，因此既有会话与工作区仍可打开。

### GUI 交付面

设置为远程主机新增一个分区：列表、添加、编辑、删除、测试连接与指纹确认。创建工作区时先选主机、再选远端目录，目录选择器通过该主机的 realm 列举其文件系统，而不是列举 Harness 主机的目录。会话界面标注主机，SSH 连接丢失时明确报告操作不可恢复且不会被重放，与运行时的不重连约定一致。

主机行的 `open` 是采样得到的事实，而不是被推送的事实。`hosts.list` 报告本进程当前是否为每台主机持有已打开的执行世界；follow 流只通告持久记录写入，而在最后一次基线之后停止的世界不写入任何记录，因此没有任何东西推送这一变化。设置区在挂载时采样，每次浏览或创建入口在寻址前采样所选世界，工作区收养在原生选择器返回后再次采样，因为 Host 记录远程工作区时并不检查该世界是否仍然存在。已停止的世界是否也应成为被推送的事件，留待第 7 阶段的断线工作决定。

### 工作区创建的主机选择

工作区创建的主机选择跨包：[ui-remote-hosts](../../../../packages/client/ui-remote-hosts/README.zh.md) 写入它，工作区浏览器、选择器与标签读取它。它在对象层作为此包注册的 Client 服务 `ctx.remoteHostSelection` 拥有，每个消费注册把裸快照源绑进自己保留的 `hooks` compartment，于是组件通过框架 hook 读取该值。声明式 store 无法承载这一事实：store handle 只属于声明它的那次注册，跨包就需要客户端规则禁止的模块级单例。

工作区包通过 `ctx.get` 读取该服务，并在其注册变化时重新绑定，因此丢掉 ui-remote-hosts 这一行的组合会继续在 Harness 主机上浏览与创建工作区，而不会因没有 fiber 提供该服务而挂起。

### 交付阶段

1. 定案本方案，并写出它所依赖的持久化与作用域决策。
2. 交付主机注册表、单个 realm 与辅助程序自动安装，可从 CLI profile 使用。
3. 交付凭证、GUI 主机管理，以及带指纹确认的测试连接。
4. 为工作区与会话持久化加入主机身份，并实现远端目录选择。
5. 把 Agent 作用域内的消费方迁到 realm，包括搜索、spill、语言服务器与终端。
6. 让 Host RPC 消费方按主机寻址：预览、变更摘要，以及 open/reveal 的降级。
7. 完成断线呈现、文档、快照，以及针对可丢弃主机的真实端到端验证。

### 录制 Web 车道钉住的呈现契约

录制 Web 车道依赖的两个 GUI 呈现事实是承重的。工作区分组标签保持为该行文本槽的直接子元素，分支标签作为其兄弟：标签与携带 `aria-expanded` 的 `treeitem` 之间出现包装元素，会破坏该车道的两跳定位器。目录浏览器对话框标题保持以标题文本作为可访问名称，主机标签放在带 `aria-hidden="true"` 的兄弟 span 中并由 `aria-describedby` 引用，因此标题会播报这份列表来自哪个执行世界，同时不改变定位器所匹配的名称。

## 备选方案

**每台主机一个 Harness 进程。** 为每台服务器跑一个独立 profile 不需要新架构，今天就能用，但它无法满足"一个 GUI 管理多台服务器"的产品要求，并且会把会话、设置与凭证按进程切分。它保留为受支持的降级路径，而不是目标形态。

**在每次能力调用上传入主机参数。** 给每个文件系统、进程与沙箱操作传入主机会改变能力 seam 及其全部消费方，还会把传输词汇带进目前只讲执行坐标的模型面与 Host RPC 面。隔离让既有 Service Definition 保持不变。

**为 SSH 材料新增凭证记录类型。** 专用记录类型自描述性更好，但 `grant` 记录已经能携带不透明 payload 并具备属主作用域的生命周期；在第二个消费方证明需求之前新增类型，会先扩大一个被无关消费方使用的持久化格式。

**把 Harness 搬到远端主机。** 在服务器上启动 `dsh` 会把模型凭证、会话存储与插件状态一起搬到执行世界；仓库已经能识别该启动方式并抑制本地浏览器打开。它解决的是另一个问题，也无法在一个 GUI 里承载多台服务器。

## 验收标准

1. 在 GUI 中录入 host、port、user 与密钥或口令后添加主机，无需手工编辑任何 SSH 配置，即可得到辅助程序已安装并通过摘要校验的就绪连接。
2. 针对远端目录创建的工作区与会话，其文件系统、bash、搜索、终端与语言服务器操作都发生在该服务器上。
3. 单个 Harness 进程内绑定到两台不同主机的两个会话使用彼此独立的文件系统与进程世界，互不可见对方的文件。
4. 主机密钥发生变化时连接失败并报告指纹差异，且绝不会被自动接受。
5. 连接丢失时报告操作不可恢复，且不重放任何操作。
6. 未注册任何远程主机的组合，行为与当前本机组合完全一致。
7. 默认组合即暴露远程主机管理，无需功能开关或配置改动即可注册主机。

## 风险

- 本方案把能力 seam 的拓扑从"每进程一个实现"改成"每主机一个实现"，牵涉服务隔离、泄漏服务拒绝，以及每个当前直接读取 `ctx.fs` 的 Host RPC 消费方。
- 会话头与工作区持久化在版本机制下变更，因此新旧记录都必须能打开。
- 摘要校验只证明安装的辅助程序与本地产物一致，并不认证恶意的远端操作系统。
- 自动安装要求远端 home 可写且存在受支持的 Node 可执行文件；没有 Node 的主机需要用户显式提供路径。
- 存储私钥与口令会在 credentials 中引入新的敏感数据面，包括日志、快照与导出配置中的脱敏。
- 每台主机都要付出一个 SSH 连接与一个辅助程序进程的代价，因此租约、清理与故障隔离必须按主机释放，而不是按进程释放。
- 默认开启会扩大默认面：凭证存储与对外 SSH 连接从 GUI 即可触达，不再有显式的可选步骤。
